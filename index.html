Multi-agent build orchestra

by moo

Map for work with one human owner, one lead and specialist seats, run from a multi-pane terminal workspace. Model names are current as of August 2026; treat IDs as snapshots and the seat strengths as the durable part.

Loop: human decides, lead briefs, specialist acts, lead verifies on disk, human keeps or cuts.

1. Flow

You (human... hopefully)
Owner of meaning

Taste, scope, gut-checks and judgement calls. Final keep or cut. Owns anything irreversible: commits, pushes, version bumps, anecdotal and live data.

↓
Lead / orchestrator
Highest-cost seat. Writes briefs, not bulk edits.

Turns intent into locked briefs with file and line anchors. Splits work by file territory. Verifies every claim against disk. Writes the record. Lead work is still writing, but briefs and verification rather than bulk edits.

↓ branches (parallel, different files only)
Precision coder
Composer 2.5 (Cursor Agent)

Surgical patches in one large or fragile file. Exact follow-through. Prefer for "replace this block, touch nothing else."

Second builder
Claude Sonnet 5, medium

Well-specified work in a separate file tree. Batch edits, data rows, self-contained modules. Runs parallel to Precision without collision.

Survey / research
Grok 4.5, medium

Finds what is missing. Sourcing with citations. Brief it to return "unknown" when evidence is thin, and it will.

↓
Verify on disk
Lead, independent of the agent's self-report

Read the file, run a checker script, count what should not have changed. Do not accept a summary as evidence.

Seats change. Someone gets promoted out of a role, or a model turns out to be wrong for the job. Ask for a flow map update the same way you ask for anything else. A stale map might get followed, so keep it updated.

3. Economics

Lead models can cost roughly eight times a cheap builder per token. Put the expensive seat on briefs and review. Put bulk edits on cheaper seats.

If the lead catches itself editing something a paragraph brief could have delegated, that is the mistake. A paragraph brief plus a diff review usually costs less than the lead producing the patch. It cuts the other way too: a lead that doesn't check the work is prone to GIGO with your money.

4. Scaffold first

Consider workspace over repo folder. Build the prototypes in the workspace and not in the repo folder, then port the working version in. Iterating in a disposable file keeps a bad pass out of the product tree.

This suits agents better than editing in place. A scaffold is one self-contained file with no surrounding code to break, so a cheaper seat can take it and a bad result is thrown away rather than reverted.

StepWhat it looks like
Version each pass Keep v3, v4, v5 side by side rather than overwriting. Comparing beats remembering and you can go back when v5 turns out worse.
Freeze what works Copy the good version to a frozen file before the next round of changes. That is your known-good reference while you experiment.
Capture the states Screenshot light and dark, wide and narrow. UI regressions hide in the state you were not looking at.
Port, do not paste The scaffold has no namespace, no house conventions and no service worker. Moving it in is its own task with its own review.

Scaffold, sidedeck, in the tool

A scaffold fakes its inputs. A sidedeck reads the real thing. It pulls live data or real source from the tool but the tool does not load it back. The dependency runs one way.

Borrowed from card games, where the side deck is a real set you own and bring but keep out of play until you swap something in. No established software term covers this shape and "sidecar" already means the opposite: co-deployed and sharing the app lifecycle.

StageReadsDelete it and
Scaffold Nothing real. Faked inputs. Nothing breaks.
Sidedeck Real data or real source. Nothing breaks.
In the tool Real and wired in. The tool breaks.

Remove it and see what stops working. If nothing does you are still outside. If the tool breaks you were editing production and did not notice.

Scaffold or worktree

Both give you a separate place on disk. A branch does not. Branches share one working directory, so switching changes the files under you and half-done work has to be stashed first. Two agents sharing one working directory will collide. Give each its own.

WorktreeScaffold
Isolates The repo. Real code, real build, separate checkout. The idea. One standalone file with no product code around it.
Use when You know what you are building. You are deciding what it should be.
Comes back by Merging. Porting. It was never the same shape as the product.
History Git keeps it. Keep versions as files so you can compare them at once.

Keep scaffolds outside whatever ships. They are workshop files. Once a feature is live and stable the scaffold is reference, not truth, so date it or bin it.

5. Territory

Two agents editing the same file at once will screw each other over and the loser is usually silent about it. Split work by file, not by kind of work.

AgentOwnsWhy
Precision coder The monolith or largest fragile file Single owner on the file where a collision hurts most
Second builder A separate source tree Smaller, self-contained files; parallel work is safe
Survey / research Docs and research output, no product code Never competes for a code file

When territories are clear you can run two builders at once. When they are not, run one at a time.

6. Lead capabilities

Whatever tool runs your panes, the lead needs five capabilities. Miss one and the loop breaks somewhere predictable.

CapabilityWhy it matters
See the roster Which agents exist, what each is working in and whether one is already busy. Without this you dispatch into a pane that is mid-task and lose both jobs.
Send a brief to a specific agent The core action. Addressed to one named seat, not broadcast.
Read what an agent actually printed Their terminal output, not their summary. This is how you catch an agent that stopped early or hit an error it did not mention.
Wait for one to finish So the lead can dispatch and go do something else instead of polling. Useful and also the single biggest source of false confidence. See below.
Name a seat New panes usually arrive unnamed. Naming them is what makes a brief addressable and a log readable a week later.
Trap: "finished" does not mean "done" Whatever status your tool reports, treat it as a rumour. An agent stopped at a permission prompt, waiting on a human, is usually reported as a settled state, so any "wait until finished" call returns and everything looks complete. On tools that take the pane title from an agent's first prompt, that title then goes stale, so name your seats yourself.

7. Verification

The lead runs the checks. What you need back is what changed and what did not change, both in plain language.

The second half is the one to insist on. An agent reporting "all 12 rows updated" is telling you about the part it was thinking about, and the failure you care about is the row it was not thinking about. "Nothing else in the file moved" can be a good or bad thing depending on dependencies.

An IDE will show you every changed line, which is worth having when you want to spot something missing. It will not tell you which of those changes were meant, so the highlights still need a sentence next to them.

Trap: stale build lies When verifying through a browser or any cached surface, clear the cache and service worker first then confirm the running page contains the new code before testing behaviour. A stale bundle will happily reproduce the old bug and send you chasing a fix that already landed.
Trap: it worked in the scaffold A scaffold will not always survive the port on the first pass. Test the UI on a refreshed page or a clean emulator before reporting it broken.

8. Vague is fine, unchecked is not

You will describe what you want in loose terms, and that is fine. The lead's job is turning it into something checkable before it goes out.

Batch size is the one number worth holding. Twelve items has been a safe number in testing. A long-horizon model can take the whole backlog, so the real question is not what it can hold but how much output you are willing to read at once at that model's price.

9. Standing rules live where agents read them

A rule stated once in chat is gone by the next session. A rule written in the wrong file is worse, because it looks enforced and is not. If a convention keeps getting violated, check whether it was ever written where the agents actually load it and whether it was scoped too narrowly. A style rule filed under "commit messages" will be applied only to commit messages, no matter how many times you restate it.

Fix it at the source: put it in the always-loaded rules file, state the scope explicitly, then broadcast it once to every live agent. Also make sure the rules file itself obeys the rule or it teaches the opposite.

10. Check before you edit

A lead flags a number for looking wrong next to its neighbours, calls it a typo and moves to fix it. The number turns out to be real, taken from a published source. The neighbours it was compared against were the only ones in the file that happened to look that way. The sample was three rows out of a hundred.

Before changing anything on the strength of a conclusion, check the whole set rather than the part that got noticed. Ask where the value came from. If it turns out to be real, say so and stop. That is finished work, not a dead end.

Outside advice gets scepticism by default. A conclusion you reached yourself often feels already true, so it needs a harder check, not a softer one.

11. Judgment stays human

Agents are good at finding and typing. They are not the ones to decide whether a change is worth making. In practice the line sits here:

  • Agents may: add new content, fill gaps, write research, make changes that are additive and reversible.
  • Agents may not: change live values that other things depend on, commit, push, bump versions or delete.

When an agent finds a real defect in live data, the correct output is a written case with evidence and a recommendation, not an edit. The human decides. This is also what keeps an unattended loop safe: it can work all night and still touch nothing irreversible.

12. What comes back that you did not ask for

A seat working through a brief sees things the lead did not anticipate. It finds a gap the brief missed, spots that the premise is wrong or reports that the thing it was sent to confirm cannot be confirmed. All three are good results even though none of them are what was asked for.

13. Unattended runs

This is generic advice, but worth a reminder: a schedule you asked for gets skipped while you are still yapping. Ask for clock times rather than intervals, since "every five hours" cannot be expressed and gets quietly reshaped into something with a hole in it. Name the times. This assumes the lead is also keeping track of what work is done versus undone.

14. Playbook

What to insist on, and what to check before you accept work as done.

  • Nothing new goes straight into the product. Scaffold or worktree first, then port. Branches are for shipping, not for isolating parallel agents.
  • Make the lead write the brief on disk with exact paths, exact strings, the verify command and forbidden actions. A brief you cannot read is a brief you cannot hold anyone to.
  • One specialist per file. Parallel across territories is fine. Two agents in one file is not.
  • Ask for the diff, not the summary.
  • Expect the run log to separate verified from not verified, and to name the platform or path nobody could test. A log that reports only success is not telling you what it cost.
  • Treat "verified" as a claim until you see the check output. Reading a file is not running the check.

15. Swap rules

Seats are roles. Swap models when someone else wins the strength test:

  • Better patch reliability in a fragile file, promote to Precision.
  • Better spec'd batch work, promote to Second builder.
  • Better sourcing and willingness to say "unknown," promote to Research.
  • Better judgment and honest self-correction, promote to Lead.

Test a new seat on one small, well-specified job with a clear checker before trusting it with anything larger. A clean first pass on a bounded task is the signal; a summary claiming success is not.
